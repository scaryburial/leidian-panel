## 10.8 v1.8 变更（修复：预设协议与订阅不可用）

> 本节记录 v1.8 相对 v1.7 的改动。所有结论都来自**在真实服务器上跑出来的证据**，
> 不是推测。测试方法见 §10.8.6。

### 10.8.1 头号根因：速度档是「VLESS + 裸 TCP + 无加密」，Xray 26.x 直接拒绝

预设 `VLESS-速度-8443` 由 `create-inbounds.py` 建为 `vless / tcp / security=none`，
订阅据此生成：

```
vless://<uuid>@154.12.82.50:8444?encryption=&security=none&type=tcp
```

把这条链接当配置喂给客户端，Xray 在**加载配置阶段**就失败：

```
Failed to start: main: failed to load config files: [...] > infra/conf:
failed to build outbound config with tag proxy > infra/conf:
vless without TLS or other encryption is prohibited
unless the server address is a private IP or domain
```

VLESS 自身不含任何加密，脱离 TLS/Reality 就是明文；Xray 26.x 因此**禁止**在公网
地址上使用裸 VLESS。这不是"不安全"，而是**客户端根本用不了**——节点在订阅里，
但永远连不上。

**改法**：
1. `packaging/create-inbounds.py`：速度档的传输从 `TCP_NONE` 改为 **Reality**（用它
   自己独立的一对 x25519 密钥与 shortId，不与 443 安全档共用）；拿不到密钥时退回
   裸 TCP 并打印警告。
2. 新增 `repair_prohibited_vless()`：`create-inbounds.py` 是**按 remark 幂等**的，
   老版本装出来的坏入站不会被新建逻辑修到，所以在创建之后额外扫描一次——把
   `protocol=vless` 且 `network=tcp` 且 `security=none` 的入站**原地**改成 Reality
   （只动 `streamSettings`，不动端口、备注与客户端）。

**实测**：修复前该节点 `http=000`（xray 拒绝启动）；修复后 `http=204`。

### 10.8.2 `2053`（VMess-安全-TLS）自签证书无 SAN，客户端必然握手失败

即 §10.7-1。自签证书 `CN=ui3344`、`No extensions in certificate`（零 SAN），
订阅链接里也没有 `allowInsecure` / pin。实测：严格校验 `http=000`。

**改法**（`internal/web/service/domain/domain.go`）：新增 `rewriteTLSCertificate()`，
`applyInbounds()` 在切 WS 入站之后顺带把该入站换成域名证书，`restoreInbounds()`
在停用域名时还原回自签证书。只改证书块，不动传输与客户端；若该入站被改成非 TLS
传输则拒绝改动。

### 10.8.3 启用域名后辅助脚本全部失联（安装器的「创建预设协议」静默失败）

面板启用域名功能后会被搬到 `8443` 并换用 Cloudflare **Origin CA** 证书，而
`create-inbounds.py` / `domain-setup.py` 都硬编码 `http://127.0.0.1:33441/ui3344`，于是：

```
urllib.error.URLError: <urlopen error [SSL: CERTIFICATE_VERIFY_FAILED]
certificate verify failed: unable to get local issuer certificate>
```

端口不对 + Origin CA 证书不在系统信任库 → 安装器的预设创建/订阅配置**静默失败**
（外层用 `|| echo` 吞掉了），升级后既不会修坏入站，也不会重建订阅配置。
（`configure-subscription.py` 直接写 SQLite，不走 HTTP，不受影响。）

**改法**（`packaging/create-inbounds.py`、`packaging/domain-setup.py`）：面板基址改为
**自动探测**（依次试 `http://127.0.0.1:33441/ui3344`、`https://127.0.0.1:8443/ui3344`），
并对本地回环**关闭证书校验**（Origin CA 证书本来也不该进系统信任库）。

### 10.8.4 启用域名后旧 IP 订阅链接一律 403

即 §10.7-2。`DomainValidatorMiddleware` 要求 hostname **全等** `subDomain`，
于是 `Host: <服务器IP>:2096` 一律 403 —— 已经存了 IP 订阅链接的客户端（含配套
安卓端）**根本拉不到订阅**，表现为「所有协议都不能用」。

**改法**：中间件改为**可变参数允许列表** + `normalizeRequestHost()`（小写、去端口、
去 IPv6 方括号）；`internal/sub/sub.go` 新增 `subAllowedHosts()`，允许列表 =
订阅域名 + `domainConfig.ip`。

**实测**：`Host: 154.12.82.50` → 修复前 **403**，修复后 **200**；
`Host: 127.0.0.1` / 未知域名仍为 **403**（校验未被削弱）。

### 10.8.5 自有域名没有进优选组 + 个别优选域名已死

`SyncPreferredHosts()` 只把通过网段校验的**第三方**域名写进 `hosts` 表，
`domainConfig` 里的**自有域名从未进入该组**；而第三方列表里有已经死掉的条目
（实测 `1.cf.cname.vvhan.com:2087` → `http=000`）。

**改法**（`internal/web/service/domain/preferred.go`）：
1. 自有域名 `fqdn` **无条件作为第一行**写入优选组；
2. 新增 `probePreferredDomain()`：对每个候选做**真实的 TLS + WebSocket 升级探测**
   （SNI/Host 用自有域名、目标端口/路径取端口最小的加密入站），**只有拿到
   `101 Switching Protocols` 才保留**；失败原因写进 `rejected` 供面板显示；
3. `filterReachablePreferredDomains()`：8 并发 + 25s 总预算，保序返回。

> ⚠️ **订正**：本节早先的草稿断言「24 个优选域名全部不可用」，那是**测错了**——
> 用 `curl https://time.is:2087/` 时 SNI 是 `time.is`，而真实客户端（以及订阅里的
> 配置）用的是**自有域名**作 SNI。用正确的 SNI 复测后，优选域名**基本都可用**
> （数据面实测 204）。真正的问题只有「自有域名不在订阅里」和「个别域名已死」。

### 10.8.6 验证方法（可复现）

```bash
# 1) 参数一致性：把订阅里每个节点的 uuid/port/path/sni/host/pbk/sid/flow
#    与入站定义逐字段对照（REALITY 的 pbk 要用私钥重新推导后比对）
# 2) 真实数据面：把订阅里的节点当客户端，起一个 xray 实例 + socks 入站，
#    curl --socks5-hostname 127.0.0.1:<socks> https://www.gstatic.com/generate_204
#    期望 204；失败时把 xray 的 stderr 打出来
# 3) 定向回归测试（不联网）：
cd /root/lp-src && PATH=/usr/local/go/bin:$PATH \
  go test ./internal/web/service/domain/ -run 'TestRewriteTLSCertificate' -count=1 -v
# 4) 实时探测测试（真的打公网）：
UI3344_LIVE_PROBE=1 UI3344_LIVE_FQDN=<域名> UI3344_LIVE_PORT=2087 \
  UI3344_LIVE_PATH=/ui3344ws \
  go test ./internal/web/service/domain/ -run 'TestProbePreferredDomain_Live' -count=1 -v
```

### 10.8.7 新增修复：Shadowsocks-2022 客户端 PSK 长度不匹配会让 xray **完全起不来**

> 本轮发现的最危险的一条：它不是「某个节点不可用」，而是**整台服务器的所有节点一起
> 下线**，且只要面板/服务器重启就必然触发。

- **现象**（真实发生）：面板重启后 xray 起不来，全部端口消失：

  ```
  ERROR - XRAY: Failed to start: main: failed to create server >
  proxy/shadowsocks_2022: create service > bad key
  ERROR - Failure in running xray-core: exit status 23
  ```

- **根因**：`clients` 表里**一个客户端只有一个 `password` 字段**，而 SS2022 的 PSK
  长度由 method 决定——`2022-blake3-aes-128-gcm` 要 16 字节，`aes-256-gcm` 要 32 字节。
  把同一个客户端同时挂到这两类入站上（面板 UI 很容易这么做）必然有一边不匹配。
  而 `GetXrayConfig()` 在 `case model.Shadowsocks:` 分支里**直接用 `clients.password`
  覆盖了入站 settings 里那个正确的密钥**，于是配置非法、xray 拒绝启动。面板已有的
  `normalizeShadowsocksClientKeys()` 只在 `AddInbound`/`UpdateInbound` 里跑，
  **配置生成路径上没有这道校验**。
- **改法**（`internal/web/service/xray.go` + `client_crud.go`）：
  1. 新增 `settingsClientPassword(settings, email)`：取入站 settings 里该 email 的密钥
     （订阅下发的就是它，优先沿用才不会让已导入的客户端失联）；
  2. 生成配置时按 method 校验每个 SS 客户端的 PSK 长度，不匹配则依次退回
     「入站 settings 里的密钥」→「按 method 重新生成」，并打印明确告警；
  3. 绝不把长度非法的配置交给 xray。
- **实测**：把客户端重新挂回 8389/8390（原先会让 xray 拒绝启动的状态）后重启面板，
  **xray 正常启动**，10 个端口全部恢复，日志给出：
  `Inbound "in-8389-shadowsocks" (port 8389): client "oexjuh3j76" 的 PSK 长度与 method "2022-blake3-aes-256-gcm" 不符，已改用可用密钥；否则 xray 会因 bad key 拒绝启动，全部节点下线`
- **仍存在的产品级限制**（v1.9 待办）：「就地救回」只保证 xray 能启动；由于
  `clients` 表只有一个 `password`，**同一客户端无法在 aes-128 与 aes-256 两类入站上
  同时正确认证**。要么把三条 SS 入站统一成 aes-256，要么让面板为「客户端 × 入站」
  维护独立密钥（需改数据模型）。

### 10.8.8 订正：Xray 26.x 已移除 `allowInsecure`，`2053` 在客户端侧无法挽救

§10.7-1 与《协议与端口说明》里「客户端需勾选『允许不安全/跳过证书校验』」的解决办法
**在 Xray 26.x 上已经失效**。实测（本机 v2rayN 自带 Xray 26.6.1，从中国大陆发起）：

```
infra/conf: failed to build stream settings for outbound detour >
Failed to build TLS config. >
common/errors: The feature "allowInsecure" has been removed and migrated to
"pinnedPeerCertSha256". Please update your config(s) ...
```

- 加 `allowInsecure` → **客户端拒绝加载配置**；不加 → 自签证书校验失败 → `000`。
- 两条路都死，所以 `2053` **必须服务端解决**：换成受信任证书（本补丁在启用域名时
  自动换域名证书），或在订阅里下发 `pinnedPeerCertSha256`（`hosts` 表已有该字段）。
- 另建议：**没有域名时不要默认下发自签 TLS 节点**。

### 10.8.9 真实客户端网络验证结果（本机 v2rayN / Xray 26.6.1，中国大陆）

用本机真实客户端内核逐个建隧道，`curl https://www.gstatic.com/generate_204` 期望 204：

| 节点 | 结果 |
|---|---|
| `8444` VLESS/REALITY（本补丁修复的速度档） | **204** |
| `443` VLESS/REALITY | **204** |
| `2087` VLESS/WS/TLS（含 24 个 CF 优选域名） | **204** |
| `8080` VMess/TCP | **204** |
| `2052` VMess/WS | **204** |
| `8388` SS2022 / `8389` SS2022 / `8390` SS2022 | **204 / 204 / 204** |
| `2053` VMess/TLS（自签证书） | **000**（见 §10.8.8） |

同时确认：**订阅走服务器 IP 也返回 200**（中间件修复对真实客户端生效）。

### 10.8.10 仍未做（建议 v1.9）

1. **「客户端 × 入站」独立密钥**（见 §10.8.7 末尾）——目前只能保证 xray 能启动。
2. **没有域名时不要默认下发自签 TLS 节点 / 自动下发 `pinnedPeerCertSha256`**（§10.8.8）。
3. **`1.cf.cname.vvhan.com` 之类的死域名**依赖端到端探测剔除；探测只在启用域名时
   跑一次，之后域名失效不会被自动清理。可考虑加定时任务。
4. **2053 换绑证书只在重新启用域名时生效**；已在线的安装需要「停用→启用」一次。
5. **取消域名功能不会清理 Cloudflare DNS 记录**（§10.7-3 未修）。
6. **安装脚本的 `/tmp` 残留**（§10.7-4 未修）。
7. **构建期注入凭据**（`-Token` / `-OtpSecret`）会把凭据写进二进制 `.rodata`，
   任何人都能 `strings` 出来。v1.8 的本机构建**没有注入**，这是有意的。
